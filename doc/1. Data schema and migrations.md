# Catalog ownership and cutover

Magento owns catalog schemas, physical OpenSearch indices and aliases. The API is a reader; it has no catalog lifecycle, import, dump or migration tooling. Redis caching, Kue queues and application validation schemas are independent and remain supported.

Use Magento indexer prefix `vue_storefront_catalog`, replacing the former `vue_storefront` prefix. Store 3 then has base `vue_storefront_catalog_3`. Set root `opensearch.index`, allowed `opensearch.indices`, selected store `storeViews.<code>.opensearch.index` and Storyblok's `storyblok.sync.index` to that base where appropriate. The checked-in default uses store 1; the generated template uses `DEFAULT_STORE_ID`. Keep local credentials out of version control.

Run in Magento, as the user responsible for its data:

```sh
bin/magento vsbridge:reindex --store=3
bin/magento vsbridge:reindex --all
```

Each entity has an alias, for example `vue_storefront_catalog_3_product`, `_category`, `_attribute`, `_cms_page` and `_taxrule`. Magento creates physical indices with generation suffixes and rolls aliases over during reindexing. API readers resolve the aliases directly; they neither parse physical names nor fall back to another alias. Repeat reindexing during acceptance to verify rollover.

Use the Node 14 source build and OpenSearch/Dashboards 2.19.0 described in [README](../README.md). The Docker host needs `vm.max_map_count >= 262144`; Magento joins `vue-storefront-api_default` and connects to `os1:9200`. Dashboards on port 5601 can use `vue_storefront_catalog_*` to inspect data. Do not delete volumes or downgrade existing engine data during cutover.

After aligning aliases/configuration, clear existing catalog output cache with `npm run cache clear`. Old cached totals can otherwise retain object shapes; current full `hits.total` and compact `total` are numeric and exact. Validate GET/POST, source filters, pagination, metadata, URL resolution and tax against real aliases. Only Petsies has local data; do not claim other brands are validated.

Storyblok manages its own complete `storiesIndex` only. Validate stories and product/category datasources separately from the unsupported `<base>_promo_campaign` phase, which must fail until a producer/replacement decision exists. GraphQL `cmsHierarchies` similarly reports the missing `<base>_cms_hierarchy` alias. Neither path redirects to another datasource.
